# 流量统计重构开发计划

> 用途：作为新会话、新分支开展重构的需求与验收依据。
> 更新日期：2026-10-19。
> 本计划描述产品行为、交互、视觉方向及交付要求，不限定具体实现方式。
> 本次按全新统计功能重写；现有页面仅作为能力参考。长期维护要求另见《流量统计长期维护与上游更新计划》。

## 一、重构目标

让普通用户能够顺着一条清楚的路径回答：

1. 这段时间用了多少流量？
2. 主要是哪些软件、哪些访问目标产生的？
3. 分别走了哪些策略组，哪些属于直连？
4. 某个时间段为什么突然增多？
5. 无法识别的部分有多少，原因是什么，哪些还能继续查看？

重构允许重新设计页面布局、图表、表格、详情和文案。保留已验证的统计正确性与基本能力，不要求沿用现有页面结构。

本次从新的统计记录开始，不读取、不迁移、不展示旧统计功能产生的记录，也不为旧格式保留专门的兼容界面或历史分类。

新分支仅隔离代码，不代表运行时的数据自动隔离。开发与试用必须与原有统计记录分开，不能因启动新版本而误读、覆盖或删除旧记录。现有订阅、代理配置等非统计资料不属于重写范围，应继续保留。

这里的“从零开始”只适用于本次重写。新统计功能正式投入使用后，后续跟随上游升级应保留新版本已经产生的统计记录，不能每次更新都重新清零。

## 二、现有能力参考与重写范围

下列能力已在当前自定义版本中实现，是新版本的需求参考。允许全部重写，不要求复用现有页面、保存方式或内部结构；其中已经解决的统计正确性问题，应转换为新版本的验收要求。

| 范围 | 当前能力 |
| --- | --- |
| 时间 | 今天、近 7 天、近 30 天、自定义日期；自定义范围最多 366 天 |
| 维度 | 域名／访问目标、应用／进程、策略组 |
| 视图 | 对象汇总、组合明细；可查看目标、策略组、进程之间的关系 |
| 流量 | 上行、下行、合计；支持数值排序及占比 |
| 筛选 | 策略组多选、全选和重置；按名称、进程路径、策略组搜索 |
| 趋势 | 按小时或日期展示流量组成，支持图例、时间段明细和键盘查看 |
| 排行 | 默认展示前 50 个普通条目，可查看全部匹配项；特殊分类单独保留 |
| 内容阅读 | 名称可完整换行、选中复制；可展示并复制已有进程路径；窄窗口可横向查看表格 |
| 导出 | 导出全部已保存的匹配记录，包含汇总、按时间明细、查询条件和完整性说明 |
| 数据管理 | 清空历史、采集启停、保留时长、域名与进程记录开关 |
| 状态 | 加载、失败重试、采集关闭、部分记录不可用、没有采样的时段等提示 |
| 正确性 | 已处理重连及清空后重复计数、停采前数据保存、长尾明细过早合并、筛选后排名等问题 |

当前统计包含应用接管的直连流量，并不等同于代理服务商的账单用量。当前页面以手动刷新更新结果。

## 三、仍需解决的产品问题

### 1. 用户看不懂分类名称

“未识别”“未归因”“其他”含义不同，当前需要阅读较多说明才能理解。新版本需要从一开始明确区分身份缺失、无法确定来源，以及仅为展示简洁而折叠的对象。

目标是让每个分类都能回答“这是什么、为什么出现、能否展开、是否计入合计”。解释靠近对应数据，不在页面顶部堆积长段提示。

### 2. 进程不等于用户认识的软件

完整路径帮助辨认，但用户仍可能遇到陌生的进程名、同名进程和共享宿主进程。当前尚未形成稳定的软件身份展示，也缺少从某个软件继续查看访问目标的顺畅入口。

目标是优先展示可信的软件名称，同时保留原始进程名和路径作为核对依据。无法可靠判断时明确说明，不把推测的软件归属当作事实。

### 3. 筛选和视图切换较重

时间、维度、策略组、指标、汇总方式和搜索平铺在一起，用户需要自己理解它们之间的关系。组合明细能排查问题，但不适合作为所有人的主要阅读方式。

目标是将常用动作放在主要位置，更多条件按需展开；用“概览—排行—详情”的路径代替反复切换下拉选项。

### 4. 页面缺少稳定的阅读层次

当前图例、长路径、提示与表格可能占用大量空间。大量数据时，用户容易失去当前关注的对象和筛选范围。

目标是先看到结论，再看趋势和主要对象，需要时再展开完整证据。

### 5. 统计可信度需要更容易判断

没有记录、正常零流量、未采集、采集中断、字段缺失以及新版本记录读取失败，不应呈现为同一种状态。某一天有部分记录，也不代表全天完整。

目标是提供简洁、可解释的完整性状态，并能进一步查看原因。

## 四、重构后的核心体验

### 1. 默认进入概览

建议采用以下阅读顺序：

- 顶部：时间范围、统计状态、最后更新时间和刷新入口。
- 流量摘要：合计、上行、下行，以及可识别流量的占比说明。
- 趋势：这段时间什么时候产生了流量，主要由哪些对象构成。
- 排行：访问目标、应用／进程、策略组三类入口。
- 详情：点击对象或时间段后，进一步查看相关分布和原始身份信息。

页面默认展示易懂的对象汇总。组合明细作为深入排查能力保留，不要求用户先理解它才能使用统计。

### 2. 时间与刷新

- 保留现有快捷范围和自定义日期能力。
- 明确显示实际查询的起止日期，而非只显示“近 7 天”等名称。
- 编辑自定义日期时区分待应用条件和当前结果，避免用户误解。
- 显示最后一次成功更新的时间；刷新失败时保留上一次结果并标明未更新。
- 今天与历史范围采用清楚的更新规则。第一版保留手动刷新；自动更新属于后续可选项。
- 跨日后，“今天”等快捷范围不能一直指向昨天。
- 变更系统时区后，已记录流量的时间含义应保持可解释；无法明确解释的历史需要提示。

### 3. 策略组多选与搜索

- 支持多选、全选、恢复全部及逐项移除。
- 多选结果表示所选策略组流量的合集。
- 已选条件始终可见、可清除，不因当前范围没有匹配记录而消失。
- 策略组选项不能只来自当前可见的少数排行榜条目。
- 支持搜索目标、软件名称、原始进程名、路径和策略组；只搜索实际可获得的信息。
- 提供清空搜索和重置全部筛选的直接入口。
- 明确区分“此期间没有记录”和“存在记录，但没有匹配当前条件”。
- 筛选后的合计、趋势、排行、占比、详情和导出使用同一范围。

### 4. 排行与对象详情

- 默认按当前流量指标从高到低排列，允许用户主动改排序。
- 切换指标后，图表、默认排行、占比和摘要含义一致；手动排序应保留并清楚标示。
- 明确说明默认只展示部分排行，提供查看其余对象的入口。
- 限制页面展示数量不能损失已保存的明细，也不能改变某个对象的真实累计排名。
- 点击访问目标，可查看相关应用／进程、策略组和时间分布。
- 点击应用／进程，可查看访问目标、策略组、原始名称和已有路径。
- 点击策略组，可查看该组内主要应用、目标和时间分布。
- 从详情返回时保留原先筛选、排序和阅读位置。

### 5. 应用与进程身份

- 能可靠识别时，主名称使用软件友好名称，原始进程名作为辅助信息。
- 不同位置的同名进程应能区分；不能仅凭名称就认定属于同一软件。
- 同一软件多个进程可以汇总，但必须有可信依据，并允许查看组成。
- 共享宿主、浏览器辅助进程等无法进一步确定来源时，解释识别边界。
- 获取不到路径时展示已有名称，并说明路径不可用；不能把“缺少路径”误报为“没有进程”。
- 从新版本开始，仅展示实际获得的软件身份信息；缺失身份不能靠猜测补齐。
- 详情应支持复制完整目标、进程名、路径与策略组。

### 6. 特殊分类与可解释性

| 分类 | 对用户的含义 | 应有操作或说明 |
| --- | --- | --- |
| 未识别目标／进程／策略组 | 有记录，但对应身份信息缺失 | 说明缺失的是哪个字段；展示仍然已知的信息 |
| 无法归因的流量 | 知道发生了流量，无法对应到具体对象 | 展示流量数值和占比，解释精度边界；没有明细时明确说明 |
| 其余对象 | 为了阅读简洁暂时折叠的实际记录 | 显示可用的对象数量，允许展开查看；不是数据丢失 |

这些分类在不同时间范围、维度和展示数量下应保持语义一致，不互相替代。对未知字段，保留其他已经明确的信息。

未归因占比只能在与当前筛选范围能够对应时展示。筛选特定策略组后，如果某部分无法确定所属组，不把它猜分到所选组；清楚说明该合计不含无法分组的部分。

### 7. 趋势图

- 时间轴连续，无记录的时间不能被压缩消失。
- 正常采集但流量为零，与没有采集记录采用不同表达。
- 一天内存在中断时，不能仅因当天有数据就宣称全天完整。
- 主要对象颜色在当前分析过程中保持稳定；特殊分类采用清楚、可区分的表达。
- 图例支持识别、突出关注对象，并与排行建立对应关系。
- 查看时间段时显示该时段合计、主要组成及完整性状态。
- 点击时间段可进入对应明细；鼠标与键盘均可完成主要操作。
- 不要求在小图里一次显示全部对象，完整明细应有明确入口。

### 8. 导出与数据管理

- 导出基于当前已经应用的筛选条件，包含全部匹配的已保存记录，不受屏幕展示数量限制。
- 文件清楚说明日期范围、筛选条件、分析对象、指标、占比含义以及完整性限制。
- 导出失败应说明原因，不将不完整结果标为成功。
- 清空全部历史需明确说明范围并二次确认；不能让用户误以为只清除当前筛选结果。
- 清空成功后各视图不再显示旧结果，后续新增记录只代表清空后的流量。
- 部分删除失败时如实提示，不报告全部清空成功。
- 保留采集开关、保留时长和隐私相关开关；明确说明开关是否影响已有历史。
- 停止采集保留停止前已有数据；重新开启不补记暂停期间的流量。
- 保存或读取异常时，说明当前结果是否完整，并提供合适的重试入口。

## 五、视觉与交互设计方向

### 信息层次

采用“概览、趋势、排行、详情”四层结构。概要内容简洁，解释按需展开。正常使用时，不让多条提示长期占据主要阅读区域；异常状态保持可发现，不因收起说明而被掩盖。

### 名称与长内容

列表优先保证对象可辨认。长名称可以合理换行或提供明确的完整查看入口，不依赖短暂停留的悬浮提示。路径等较长辅助信息放在次要层级或详情中。完整内容始终能够查看、选择和复制。

### 布局与一致性

沿用应用整体的视觉语言，同时允许重新设计统计页面。适配明暗主题、长名称、多选条件较多、大量记录和小窗口。主要动作不被挤出可视区域；必要的横向滚动应有明确边界。

占比条必须与标注的占比表达同一含义。数值单位与小数精度统一，零值、极小值和较大值均可读。不能只依赖颜色表达对象、异常或当前选择。

### 状态设计

至少覆盖：首次使用、加载、刷新、正常结果、正常零流量、无记录、无匹配、采集关闭、某类记录关闭、部分时段缺失、身份信息不足、读取失败、保存失败、导出中／失败、清空中／失败及新版本记录不可用。

每个状态都应说明“发生了什么”和“接下来能做什么”，不暴露内部标识作为用户文案。

## 六、不可退化的统计原则

- 同一段流量不因切换页面、改变筛选、刷新或重新连接而重复计入。
- 清空历史后，不重新出现清空前活动连接的累计流量。
- 统计合计、时间分布和对象分布在相同范围下可以核对。
- 某个身份未知时，不丢弃其他已经明确的身份信息。
- 为了展示简洁而折叠记录，不应永久损失明细或扭曲长期排行。
- 已结束时段的结果不因后续查看操作发生变化；发现数据不完整时明确标示。
- 不把没有采集到的数据视为确定的零，也不虚构缺失明细。
- 直连与代理的含义可辨认，不将统计合计宣传为服务商账单数值。
- 无法可靠判断软件身份时，保持真实信息及其边界。

## 七、范围与优先级

### 第一优先级：统计可信且基本能力完整

从零实现并验证统计正确性；完成新旧统计资料隔离、统一口径、明确的软件／进程身份、特殊分类解释、多选筛选、搜索、完整阅读复制、导出及数据管理。

### 第二优先级：重建主要分析路径

完成新的页面层次、概览摘要、趋势与排行联动、对象详情、时间段详情、条件保留、状态反馈和明暗主题／窄窗口适配。

### 后续可选增强

自动更新、时段对比、常用筛选保存，以及更丰富的软件身份识别。只有在基础能力完成后再安排，不作为本次完成的必要条件。

不纳入本次目标：旧统计记录读取、迁移、历史格式兼容与恢复，服务商账单对账，多设备统计汇总，以及与流量统计无关的应用功能调整。

## 八、实施阶段与交付物

| 阶段 | 工作重点 | 交付与退出条件 |
| --- | --- | --- |
| 0. 确认维护基础 | 确认上游版本、新版本开发起点、统计资料隔离及后续更新路径 | 新版本可持续接收上游更新；原有资料与工作成果有保留位置 |
| 1. 需求定稿 | 对照现状确认保留能力、名词、范围、特殊分类及统计边界 | 一份统一的功能与口径清单；明确必须项和可选项 |
| 2. 交互与视觉方案 | 重新组织概览、趋势、排行、详情、筛选和异常状态 | 可供评审的页面方案，覆盖明暗主题、窄窗口、长名称和缺失信息 |
| 3. 核心统计与身份 | 保证合计可信，明确软件／进程和特殊分类，确认新旧统计资料互不影响 | 关键场景结果可核对，查看操作不会改变历史含义 |
| 4. 页面与完整流程 | 完成筛选、查询、联动详情、复制、导出和数据管理 | 从进入页面到定位对象、导出结果的流程可完整操作 |
| 5. 验收与交接 | 检查正确性、交互、视觉及异常场景，整理剩余限制 | 验收清单、实际结果与已知限制；更新使用说明 |

每个完成且验证通过的阶段及时提交并推送，保留可回溯的工作成果。阶段顺序可按实际需要调整，但不能跳过统计口径确认和最终验收。

## 九、核心验收场景

| 场景 | 通过标准 |
| --- | --- |
| 第一次进入统计 | 能看懂统计范围、当前时间范围和主要流量来源 |
| 软件名称陌生 | 能查看原始进程名及已有路径；不错误宣称它属于某款软件 |
| 同名进程 | 可区分不同身份，无法确认同一软件时不擅自合并 |
| 长名称与长路径 | 能完整查看并复制，窄窗口也能操作 |
| 多选策略组 | 所选组合的摘要、图表、排行、详情和导出一致 |
| 切换日期或维度 | 筛选条件仍可理解和清除，不出现隐藏条件造成的假空数据 |
| 搜索后无匹配 | 显示无匹配状态，并能直接清除条件 |
| 切换上行／下行 | 默认排行、图表和占比对应所选指标，手动排序有明确提示 |
| 大量对象 | 展示数量不影响真实累计值与完整导出，长尾对象可继续查看 |
| 特殊分类 | 能区分信息缺失、无法归因和可展开的其余对象，不把旧版历史概念带入新界面 |
| 某时段没有采集 | 不呈现为确定的零流量，完整性说明与详情一致 |
| 刷新失败 | 保留已有结果，明确未更新并可重试 |
| 断开后恢复 | 不重复计入原有流量，不补造中断期间的明细 |
| 暂停及恢复采集 | 暂停前已有数据保留，暂停期间不被事后累计进来 |
| 清空历史 | 确认范围明确；成功后没有旧记录回流；失败时准确反馈 |
| 关闭身份记录 | 新记录遵守设置，已有历史是否保留有明确说明 |
| 导出当前分析 | 日期、条件、指标和全部匹配记录可核对，并保留完整性说明 |
| 本次首次使用 | 从新记录开始，不要求旧记录出现在新统计中，也不误读、覆盖或删除旧资料 |
| 新版本记录异常 | 不导致整个页面失效；不可用内容有说明，正常记录可继续查看 |
| 后续上游升级 | 统计入口与功能保留，新版本已产生的记录、设置和非统计配置继续可用 |
| 跨日与时区变化 | 日期标签、实际查询范围与历史含义一致，不能解释的部分有提示 |
| 明暗主题及小窗口 | 内容可读、主要动作可达、没有不可恢复的遮挡或裁切 |

## 十、长期跟随上游的交付要求

本次重写必须以“上游可以持续升级，统计功能可以持续保留”为前提，而不是只完成一个固定版本的页面。

- 保留可追溯的上游版本来源，以及独立可辨认的自定义统计改动。
- 统计功能尽量集中管理；与原系统相接的部分应有明确清单，避免零散修改难以找全。
- 允许调整必要的系统入口，但不要为了统计重做无关页面和基础能力。
- 上游更新先在独立的升级验证版本中处理，确认原系统和统计功能都正常后再作为日常使用版本。
- 日常使用的安装包应来自自己的维护版本。更新提示和安装行为必须说明版本来源，不能把带统计的版本悄悄替换成官方原版。
- 每个可用版本都保留源代码、安装包和回退依据；升级遇到问题时能够回到上一个可用版本。
- 区分“程序回退”和“统计记录回退”：回到旧程序前，应明确新记录能否继续使用，不能默认程序回退就能恢复所有资料。
- 验收中必须包含一次从选定上游版本到后续上游版本的升级演练；如果尚无新的合适版本，应明确记录未演练项，不能宣称已经验证长期更新能力。

维护流程见[《流量统计长期维护与上游更新计划》](traffic-stats-maintenance-plan.md)。本计划不要求在重写期间修改现有使用环境的更新设置。

## 十一、新会话启动说明

请基于本计划，在新的重构分支开展流量统计重写。先阅读《流量统计长期维护与上游更新计划》，确认有上游历史的干净版本作为开发起点；保留当前自定义版本作为参考和回退依据，再整理功能口径并提出交互和视觉方案，随后分阶段实现和验证。

允许重新设计页面与内部实现，不要求沿用现有布局。以已经验证的统计正确性作为验收标准，从新记录开始，不承担旧统计记录读取、迁移、格式兼容与恢复。开发运行与原有资料隔离，不误动订阅和代理配置。正式使用后，未来升级应保留这次重写版本产生的记录。

优先解决用户看不懂流量来源、应用／进程难以辨认、特殊分类不清楚、长名称阅读复制不便和筛选分析路径繁琐的问题。必须保留策略组多选及筛选、统计、导出的一致性。

本次完成以必须项和验收场景为准，不因可选增强无限扩大范围。每轮完成并验证后及时提交、推送；交付时说明实际验证结果及剩余限制。
