# 流量统计长期维护与上游更新计划

> 更新日期：2026-10-19。
> 与《流量统计重构开发计划》配合使用。本文描述版本维护、更新与交付规则，不规定统计功能的具体实现方式。

## 一、先区分四件事

| 对象 | 它解决什么 | 它不会自动解决什么 |
| --- | --- | --- |
| 新代码分支 | 隔离重写过程中的代码改动 | 不会自动隔离本机统计资料，也不会自动具备顺畅的上游更新基础 |
| 上游源码更新 | 获得官方新功能、修复和维护成果 | 不会自动验证自定义统计还能使用 |
| 自定义安装包 | 将“官方基础能力＋自己的统计功能”交付到使用环境 | 安装官方原版不会自动带上自己的改动 |
| 统计记录与设置 | 保存实际使用过程中产生的资料 | 代码推送不等于记录已经备份，程序回退也不等于资料已经回退 |

因此，长期保留统计功能需要同时管理源码、可用安装包、更新来源和使用资料。

## 二、当前仓库的实际情况

- 自定义工作位于 `feature/traffic-stats`，已推送到自己的仓库。
- 当前自定义分支的起点是包含统计增强的独立初始快照，并未保留它与上游主线的共同提交祖先。
- 仓库中另有上游来源的历史和版本引用；这些引用不能仅凭名称就视为当前已同步到最新官方状态。
- 当前只配置了自己的仓库地址，尚未单独配置正式的上游来源。
- 当前应用内更新仍指向官方发布渠道。安装官方原版会替换自定义程序，自己的统计能力不会自动进入官方安装包。

这些问题不能只靠“在当前分支再拉一个重写分支”解决。新分支如果仍从独立快照出发，会继续继承同样的维护困难。

## 三、本次重写的推荐起点

利用本次允许从零重写的机会，先确认一个正式、干净、带完整上游历史的版本，再从它开始新的自定义维护线。

- 确认正式上游是 Clash Verge Rev 官方项目，并记录所采用的明确版本。
- 优先选择已确认适合日常使用的正式版本，不仅根据分支名称或版本文字判断来源。
- 保留当前自定义分支作为现状参考、需求依据和旧版本回退资料，不重置或覆盖它。
- 将本次重构计划带入新维护线，重新实现统计功能；现有实现可参考，但不把整套旧快照当作一个巨大更新混入官方基础。
- 当前导航名称、安装包调整等个人改动单独列清单，逐项决定是否继续保留，不默认为统计功能的一部分。
- 重写和初次试用使用独立的统计资料，从新记录开始；旧统计记录不迁移，订阅及代理配置不在清理范围内。

这样建立后，后续上游更新可以沿着清楚的版本关系进入自定义维护线，不需要每次从新官方版本重新手工拼接全部代码。

## 四、长期维护的版本分工

| 版本线 | 用途 | 维护要求 |
| --- | --- | --- |
| 上游参考线 | 记录官方版本及官方历史 | 保持纯净，不放个人统计改动 |
| 自定义日常使用线 | 保存官方基础能力和已经验证的统计功能 | 作为自己的安装包来源，持续保留记录和设置 |
| 功能开发线 | 重写或新增统计能力 | 验证后进入日常使用线，阶段成果及时提交推送 |
| 升级验证线 | 尝试引入某次官方更新 | 独立检查冲突和行为变化，验证通过后再进入日常使用线 |
| 已发布版本 | 标识已经实际可用的交付结果 | 可找到对应源代码、安装包、上游版本与回退说明 |

不要求每个官方改动都立即跟进。以正式版本更新为主；需要提前接收关键修复时，单独评估其影响。

## 五、每次更新的固定流程

1. 查看目标官方版本的变化，确认要解决的问题和可能影响统计的范围。
2. 保存当前可用版本、安装包及必要的使用资料备份，确认回退方式。
3. 在升级验证线引入上游变化，并处理原系统和统计功能之间的冲突。
4. 按清单验证原系统基础功能、统计正确性、统计页面、筛选、导出和设置。
5. 确认本次重写版本已经产生的记录仍可使用，新的记录继续正常累积。
6. 生成自己的候选安装包，实际安装并检查版本身份、更新提示和统计入口。
7. 验证通过后，将其标为新的日常使用版本，保存源代码和安装包。
8. 更新维护记录，注明采用的上游版本、需要手工处理的地方以及遗留限制。

发生冲突时，按两边改动的实际含义处理；不能默认全部采用官方版本或全部保留自定义内容。

## 六、让后续升级更省力的约束

- 尽量把统计能力集中管理，清楚列出它与原系统连接的位置。
- 统计以外的外观偏好、安装调整和其他个人功能保持独立，方便判断升级影响。
- 不把上游版本更新和大量统计改造混在同一次难以解释的变更中。
- 维护一份自定义改动清单，说明每项改动的用户价值、影响范围和验证方法。
- 为最重要的正确性要求保留可重复验证的检查方式，减少每次升级从头排查的成本。
- 如果上游以后提供相似能力，先评估取舍，再决定保留、整合或退出自定义部分。

没有任何分支或目录安排能保证永久没有冲突。目标是把冲突限制在少数明确位置，并让每次处理都可验证、可回溯。

## 七、应用更新与安装包规则

正式投入使用前，必须选择一个明确的自定义版本更新方式：

- 初期建议手动安装自己验证过的安装包；应用内不得引导用户不知情地安装会替换统计能力的官方版本。
- 后续如果提供自动更新，更新来源应是自己的自定义发布渠道，不能继续把官方原版当成自定义版本升级包。
- 上游有新版本可以作为“有待适配”的信息提示；适配并验证完成后，才属于自己的可用升级。
- 自定义版本应能辨认采用的官方基础版本和自己的统计功能版本。
- 发布和安装过程要兼顾已有配置、统计记录、失败恢复及版本回退。

这部分保护的是安装到电脑上的实际功能。仅仅把代码保存在自己的仓库，不能阻止官方安装包替换本机程序。

## 八、数据规则

本次重写与日后的正常升级采用不同规则：

| 情况 | 处理要求 |
| --- | --- |
| 本次从旧统计重写 | 从新的统计记录开始，不迁移旧记录；新旧资料互不误用 |
| 开发与日常使用并行 | 开发活动不能改坏日常使用资料 |
| 新统计功能的常规更新 | 保留已经产生的新记录和设置 |
| 新统计功能未来调整资料规则 | 明确处理方案、可用范围及回退影响，不默认可以丢弃 |
| 程序升级或回退 | 事先说明资料是否可继续使用，并保留必要备份 |

不把全部应用资料清空当作解决统计兼容问题的方式。

## 九、首次交付与每次升级的检查项

- 能找到所采用的官方版本，保留可追溯的上游历史。
- 能明确辨认自定义统计的改动和其他个人改动。
- 原系统基础使用正常，统计入口及核心分析流程正常。
- 重连、暂停恢复、刷新和清空不会造成重复累计或旧记录回流。
- 当前记录、设置、筛选和导出结果可核对。
- 安装后仍是自己的自定义版本，后续更新来源明确。
- 升级失败时能找到上一个可用安装包及资料恢复说明。
- 源代码已经提交推送，对应安装包和维护说明已经保存。

## 十、新会话应先做什么

先确认干净上游版本、当前独立快照与上游的历史关系，以及新旧资料隔离方式。保留当前工作成果，然后建立新的自定义维护起点，再按重构计划开始设计与实现。

不要仅从当前独立快照拉新分支后，就默认上游更新问题已经解决。不要为了整理历史而覆盖当前已推送分支，也不要未经说明直接改变当前日常使用环境。
