## 1. 目标与取舍

用户需要查看大体代理流量，找出规则遗漏或分流不合理的大流量地址，辅助核对机场用量。性能、内存和存储占用的权重略高于统计精度；不追求逐包计费。

用户可以接受每天几 MB 的误差。这是期望的量级，不是在现有快照接口上已经证明的上限。先实测，再披露偏差；不可把未采集部分包装成精确的零。

必须实现：

- 代理地址排行，支持上行、下行和合计排序。
- 查看地址关联的进程、命中规则、策略链和出口。
- 今天、最近一小时、近七天、近三十天；搜索和分页。
- 后台持续采集，页面自动刷新，关闭页面不停止统计。
- 保留每日用量，辅助与机场相同周期、相同单位的用量比较。
- 低开销存储、清理与普通升级后的历史保留。
- 自动发现官方正式版、合并验证、构建自己的安装包和自定义更新渠道。

不实现：异常告警、异常评分、通知、自动改规则、抓包、内核补丁、网站品牌推断、进程背后的标签页或扩展识别、多设备汇总、订阅账单抓取、自动认定机场多扣费。

## 3. 模块边界与技术选型

```text
官方 Mihomo 连接接口
  -> adapter：统一连接字段、身份及出口类型
  -> collector：连接基线与非负增量
  -> aggregator：分钟汇总、每日摘要、采样状态
  -> store：独立线程 / SQLite / 批量事务
  -> query：后台聚合、筛选、排序、分页
  -> Tauri 命令 / 前端 services
  -> 地址排行页面与对象详情
```

### 3.1 后端

- 使用现有 Rust、Tokio、Tauri 和 Mihomo 插件，不另起常驻服务。
- SQLite 驱动首选 `rusqlite`，使用与项目构建兼容的锁定版本；无 ORM、无前端 SQL 插件。先检查工作区已有 SQLite 依赖，能复用则复用。
- bundled SQLite 为优先构建方式，避免要求用户单独安装数据库；阶段 1 核验与现有原生链接依赖是否冲突。
- SQLite 连接由独立工作线程持有，通过有界消息队列收取批次和查询；禁止在 Tokio 异步执行线程上直接进行阻塞 SQL 或文件操作。
- 单写入者，查询先复用同一所有者串行执行。只有实测需要时才增加只读连接。
- 全新模块按 `adapter`、`collector`、`aggregator`、`store`、`query` 职责组织；模块路径在旧代码退役时统一，不沿用旧实现作为骨架，不重构无关系统。

### 3.2 前端

- 复用 React、TypeScript 和 Material UI，不新增图表、全局状态或表格依赖。
- `services/traffic-statistics` 负责命令、传输和数据契约；页面只持有筛选、分页和展开状态。
- 配置与清空等变更走已有 intent/mutate 通道。若使用事件，遵守 services/bus 和 store 的所有权，不在组件自行重复订阅。
- 普通查询使用当前请求序号防止旧响应覆盖新条件；同一页面不并行堆积轮询。

### 3.3 与上游的接入点

只允许必要的启动/退出、命令注册、导航/路由、本地化、发行配置和构建接入。维护实际接入文件列表；统计逻辑不进入原连接页面、首页或代理管理。

继续使用官方内核。内核接口变化由 adapter 吸收。自定义发行配置拥有版本、更新地址和签名公钥，移除统计模块对更新策略的直接控制。

## 4. 采集与计数合同

### 4.1 采样调度

- 默认一秒一次，保留现有量级；页面不创建采集循环。
- 同一时刻最多一个连接请求；超时后按现有后台策略处理，不补发堆积 tick。
- 页面可见时每五秒查询一次；隐藏/卸载停止查询，恢复后立即刷新。
- 若其他后台消费者已有可用快照分发机制则共享，否则由统计后台单独拥有一个定时请求，不为共享而重构原连接系统。

### 4.2 连接基线

- 身份使用内核会话代次、连接 ID、连接开始时间。活动连接表只保存必要字段和计数，消失后及时释放。
- 首次启用、主动恢复采集、清空以及确认内核重启后建立基线，不把之前的累计量一次计入。接口短暂断开不等于主动停采或内核重启。
- 正常快照计算累计字节差，不对速率积分。新连接仅在其开始时间可靠地落于连续采样区间时，从零计算；否则先建基线。
- 计数倒退视为重置或异常，重建对应基线并记录状态，不产生负数，不以 lifetime 值补偿。
- 短暂变慢且会话连续、计数可信时可累计增量，但时间只归到观测结束桶；不能宣称知道缺口内精确时间分布。
- 单次请求失败不清空全部连接基线。能确认同一内核会话、连接 ID/start 相同且计数单调时，恢复后继续累计上次成功观测以来的增量；标记时间分布不准确，不主动丢弃可恢复的大流量。
- 通过应用实际生命周期代次及可获得的内核身份核实会话；重启、身份不可靠或计数重置时才重建相应基线。已消失且没有最终计数的连接不补造来源或字节，仍存在的可信连接不受牵连。
- 失败、恢复后的累计区间和不可恢复缺口分别记录。跨桶恢复增量归到观测结束桶并说明时间精度，不能把缺口呈现为正常零流量。
- 关闭前提交已采集数据；暂停后不事后补记暂停期间的流量。

### 4.3 代理、直连和规则

- route 为 `proxy`、`direct`、`unknown`，不得根据策略组名称判断是否代理。
- 核对实际使用内核版本的 chains 顺序及内建出口语义；为嵌套组、DIRECT、REJECT 等保存真实快照证据。
- 不确定的出口保留原始链并标为 unknown，不默认算代理。嵌套链只计一次，不按经过的每个组重复累计。
- 保存规则类型、规则内容和策略链。规则缺失表示未提供，不能伪造为规则未命中。
- 默认排行只取 proxy；允许切换 direct/unknown，所有摘要、排行、详情及导出遵循相同条件。
- 全局累计值只作为采样诊断，不作为代理总额，不把其差额归给地址、进程或机场。
- 全局与连接不一致时保留观测到的连接增量，并标记区间；不能因全局比较失败清空全部来源。连接自身重置等无效增量仍需排除。

### 4.4 目标与进程身份

- 域名优先用于地址排行，没有域名则用 IP；不做 DNS 反查和网站品牌推断。
- 域名规范化只做经过验证的大小写、尾点等处理，不粗暴截最后两段，不自动合并所有子域名。
- 保留域名关联的目标 IP 供详情核对，不能因为 CDN IP 改变把同一域名排成多个主条目。
- 进程以路径和原始名称区分，缺路径时保留名称并显示限制；不把缺路径进程自动合并到已知路径软件。
- 策略配置变化后，按实际记录的规则身份分别累计，不用当前配置重写历史解释。

## 5. SQLite 数据模型与资源控制

逻辑模型如下，精确字段和索引由阶段 1 的查询计划及基准确定：

| 表 | 内容 | 保留方式 |
| --- | --- | --- |
| meta/settings | 格式版本、采集设置、报表时区、清空代次 | 持续保留 |
| targets | 规范化目标及类型 | 引用复用，过期后回收 |
| processes | 进程名称与已有路径 | 引用复用，过期后回收 |
| routes/rules | 出口类型、链、规则类型和内容 | 引用复用，过期后回收 |
| minute_usage | 分钟 × 目标 × 进程 × 规则/出口 × IP 的上下行、最近活动 | 最近 24 小时 |
| hour_usage | 按固定报表日界对齐的小时区间，保留身份组合及 UTC 起止时刻 | 最近 30 天，避免和 minute 重复查询 |
| daily_usage | 报表日 × route 的无身份筛选上下行摘要 | 最近 30 天，仅加速独立日报 |
| sampling_status | 合并后的采样区间、缺口与重置状态 | 与查询保留期一致 |
| ingest_sessions | 批次序号与提交状态 | 仅保留去重所需信息 |

实现要求：

1. 所有字节使用整数；分钟转小时采用求和，不做主动舍入。
2. 每个身份组合使用唯一键；索引优先覆盖时间范围及目标详情，不给所有文字建立额外索引或全文搜索。
3. 按完整累计值排序再分页，默认 50 行；不在采集时截前 N 名。
4. 默认每分钟批量事务。阶段 1 测试 WAL + synchronous=NORMAL 的兼容性、占用和异常退出表现；它可能损失最近事务，不提供断电不丢保证。
5. 页面查询包含已接收的内存增量与已提交记录，使用统一快照边界，不能重复叠加。返回 observedAt、savedAt 和 pending 状态，不因五秒查询强制写盘。
6. 批次带运行会话和递增序号，在一个事务内更新用量与最后提交序号；提交成功但应答失败时重试不得重复加账。不另造复杂事件日志。
7. 滚动合并、删除旧桶和更新时间水位放在同一事务；中断后重试不重复、不丢失，不让同一区间同时读 minute 和 hour。
8. 近期数据全用 minute；聚合桶结束满足 24 小时保留要求后才降采样，允许最多多保留不足一小时。查询依据水位选择互不重叠的 minute/hour 区间，返回实际粒度。
9. 报表时区在首次初始化固定并显示，默认采用本机时区；系统时区变化不自动重写历史日报。第一版不提供复杂时区编辑。历史聚合桶以每个报表日的 UTC 起止时刻为界，日内按最多 3600 秒切分，最后一桶裁到日终，禁止跨日。保存 UTC start/end 和 report_date，夏令时重复小时用 UTC 区间区分，不以本地小时文字为唯一键。
10. 日报直接由原始增量按报表日累计，日界与 minute/hour 归属采用同一函数。今天、近七天、近三十天按固定报表日查询；最近一小时用近期分钟桶并披露分钟边界精度。历史自定义日期只接受完整报表日，不承诺从小时桶还原任意分钟边界。
11. 定时小批清理及 checkpoint，复用空闲页；不每分钟 VACUUM。磁盘占用包含 db、wal、shm、备份和旧资料，不只看主文件。
12. 排队、待写和身份缓存有明确的数量/字节上限。写盘持续失败时保留有界待写批次；到上限暂停新统计，显示具体原因，恢复后重建基线。禁止影响代理转发或静默丢批次。
13. 磁盘空间不足或容量保护触发时不自行删除未过期历史，不悄悄合并掉长尾来源；按同样的暂停与恢复机制处理。

正式容量阈值在基准后定稿。不要为了一个未经验证的体积目标引入有损排名算法。

## 6. 页面、查询及用量对比

### 主页面

- 顶部：时间范围、代理/直连/未知范围、采集状态、最后更新时间。
- 摘要：当前范围上行、下行、合计；明确单位和采样口径。
- 地址表：域名或 IP、下行、上行、合计、最近活动。默认合计降序，支持上传/下载排序。
- 搜索地址、IP、进程和规则；输入防抖；排序和分页在后端执行。
- 点击地址展开进程、IP、命中规则及出口分布，支持复制完整地址、路径和规则。
- 不将全局无法归因差额混入代理排行。采样缺口、未知出口只用紧凑状态显示，不加入告警系统。
- 第一版不新增复杂趋势和多维透视图；定位大流量地址优先。

### 每日汇总与机场对照

- 提供独立日报列表和完整报表日期范围合计，使用相同报表时区及 route 口径。日报明确标注“全部地址”，不继承主排行的地址、进程、IP 或规则搜索；daily_usage 不回答身份筛选查询。
- 某个地址的按日明细按同一身份条件从 minute/hour 记录聚合，不能读取全量 daily_usage 冒充筛选日报。只有时间、route、身份条件均相同时才要求合计一致。
- 可以复制数值或导出当前范围的 UTF-8 JSON；复用公共保存对话框能力，新写导出数据协议，不新增表格依赖。
- 默认导出摘要与地址排行；需要明细时显式选择，分批处理而不是一次装载全部历史。
- 对比前统一起止时刻、MB/MiB、上行+下行、节点倍率；工具记录本地观察值，不自动折算机场账单。
- 说明协议开销、短连接/结束尾部漏采、停机和采集缺口可能影响差额。订阅或机场身份不猜测归属，多机场合并统计不能当作单机场账单。
- 每日几 MB 是用户可接受量级，不把观测误差与机场账单差额混为同一指标，不自动判定多扣费。

### 设置与状态

新实现只保留采集启停与清空，保留时长先固定为上述默认值，不因旧版存在某项设置就自动保留。首次开启说明会记录目标、进程和规则。清空需确认，代次切换与排队数据串行化，成功后旧批次不能回灌。

区分首次使用、停采、未采集、零流量、搜索无结果、读取失败、保存积压、容量暂停和刷新失败。刷新失败保留上次结果及更新时间。文字可复制，适配深色及窄窗口。

## 7. 旧资料、数据升级和回退

- SQLite 使用独立的新格式目录，例如 `traffic-statistics/v2/usage.sqlite3`，最终路径在阶段 0 复核后确定。
- 本次切换从新记录开始，不自动导入旧 JSON，不覆盖或删除旧资料。启动时明确记录起点及旧记录保留位置。
- 本次是明确的格式切换；以后正常上游升级不得再换目录清零。
- 用 schema version 管理后续迁移，迁移前创建一致性备份（SQLite backup API 或关闭连接后的安全复制，不直接复制活跃主文件）。
- 未知新格式拒绝写入；迁移失败保留原库、报告错误，不自动创建空库覆盖。统计失败不阻止代理正常启动。
- 程序回退和数据回退分开说明；仅在新程序未产生数据或用户明确选择恢复旧快照时回退数据，不能悄悄丢掉升级后的记录。
- 开发运行使用独立资料根目录。订阅、代理和系统配置不进入统计清理范围。
- 升级前同时备份统计库和应用拥有的配置、订阅资料及必要设置，记录旧程序、内核与服务版本。在退出或持有配置所有权时取得一致副本，不覆盖用户指定的外部资料。备份可能含订阅凭据，只保存在本机，不上传 CI 或发布产物。
- 演练上游配置迁移和配套内核变化，明确旧程序能否读取新资料。不兼容时列出回退所需配置快照及配套组件，并保留升级后资料，不能承诺只安装旧包即可无损回退。
- 客户端自动安装必须在本机备份成功后进行；失败则保留当前版本并报告。现有更新器若无此接入能力，阶段 4 先补齐，不用发布端测试替代用户机器备份。

## 8. 自动跟随上游及发行方案

### 8.1 版本线

- 保持官方历史作为参考；自己的维护线始终包含已验证的统计功能。
- 从自己的维护线建立每次升级分支，merge 明确的官方正式版提交；不 reset 到官方，不每次重放整套统计代码。
- 每次构建记录官方 tag/commit、自定义 revision 和统计 schema version。
- 自动模式只接受版本前进且目标提交包含当前官方基准的正式版；旧版目标、同 tag 改指、非前进历史停止并报告。合并祖先提交不会直接回退代码，但不能因此发布来源标识错误的新包。
- 自定义程序版本必须单调可比较，不能只用 SemVer build metadata 区分更新。先验证 Tauri/Windows 的版本限制，再确定单调发行号与“官方基础版本”的显示方案。

### 8.2 同步流水线

使用独立的自定义 workflow，尽量复用现有构建能力。自定义标签为 `stats-release/<发行号>`，不匹配上游现有 `v*.*.*` 触发器；官方参考标签为 `upstream/<官方tag>`。

阶段 0 盘点继承的 release、autobuild、updater、通知等可发布工作流的触发器、仓库/分支条件与写入目标。在 fork 中给非自定义发布任务设置官方仓库条件或停用其发布任务。不能只靠标签前缀，因为手动、定时和分支 push 也可能触发。自定义更新清单生成器只消费自定义发行记录，不无过滤扫描所有标签。每次合并上游后重新验证隔离。

同步步骤：

1. 每日检查官方非草稿、非预发布正式 Release；支持手动指定正式 tag。
2. 将目标 tag 解析并固定到 commit，检查是否已处理，避免重复分支和重复发布。
3. 从当前维护线建立/更新唯一升级分支，合并该官方提交。冲突时保留证据并停止，不自动 ours/theirs。
4. 显式调用复用验证工作流，不依赖 bot push 再触发其他 CI；任务串行化并再次确认基础提交未变化。
5. 验证原应用构建、统计数据接口、计数行为、旧库读取、统计页面、发行身份与更新来源。
6. 初期生成候选包和 PR，完成一次真实安装升级演练后，才启用无冲突且所有门禁通过的自动合并/发布。
7. 后续正常升级自动发布；冲突、检查失败、迁移变化或打包异常停止升级，现有可用版继续使用。

工作流自动写入的提交和 PR 文案使用英文、遵循仓库 issue 与 AI disclosure 规则；PR 链接既有需求 issue。准备流水线时核验实际 Actions 权限、默认分支和分支保护，不能假定 fork 已允许定时任务。

### 8.3 自定义发布与客户端更新

- 第一交付目标为本机 Windows x64，不照搬上游所有平台、Winget、Telegram 和镜像发布任务。统计代码保持跨平台，其他平台发行另验。
- 安装身份和资料目录保持稳定；不同发行渠道的安装切换只做一次经过验证的过渡，不暗改用户目录。
- 自己的安装包、自定义更新清单、更新签名密钥/公钥成套管理；公钥在客户端，私钥只放发布 secrets。
- 更新清单只包含自己的可用包，不回退到官方原版地址；已有官方更新缓存必须失效或按新签名拒绝，不能继续安装。
- 先上传完整安装包和签名，再验证可下载、签名和版本匹配，最后发布更新清单。失败时不改变旧可用清单。
- 分离合并验证与持有签名密钥的发布权限；合并 PR 的构建不能直接读取发布私钥。发布针对已验证的固定提交。
- 更新地址和公钥是发行配置，不是统计模块常量；移除 MANUAL_UPDATES 的临时限制前，先验证自己的整个更新链路。
- 客户端可自动检查、下载，按现有应用体验在合适时机安装；不得为了统计另建下载器或强制中断代理。
- 保留上一个可用安装包和对应源码。首次密钥、Actions secrets、发布权限配置属于明确的部署前置项，缺失时给出候选包，不伪称自动升级已可用。

## 9. 实施阶段与退出条件

| 阶段 | 具体任务 | 退出依据 |
| --- | --- | --- |
| 0：范围与基线 | 关联需求 issue；确认当前分支、资料目录、内核版本和最新目标正式版；捕获真实连接字段；记录禁用统计时资源基线 | 确认开发不触碰日常资料；列出实际接入文件；可重复的连接样本和基线数据 |
| 1：存储与接口小验证 | 验证 rusqlite 原生构建；实现最小批量写入、聚合查询、分钟降采样；测 WAL/内存/耗时；定稿 schema、索引、时区和容量阈值 | 驱动构建通过；重复执行不重复加账；资源和查询实测支持选型，否则先调整再全面开发 |
| 2：采集与持久化 | 从零实现 adapter/增量/route/规则记录；队列和失败恢复；分钟、小时、日报；重启、暂停、清空和退出落盘 | 正常大流量可追到目标与规则；已知重置不重复计数；所有失败路径不影响代理 |
| 3：查询和页面 | 从零实现查询协议、后台筛选聚合分页和页面；地址表、详情、日报、复制/导出；可见性轮询和必要状态；替换复杂旧入口 | 用真实大流量能沿排行找到地址、进程和规则；内存不随完整历史线性增长 |
| 4：自定义发行 | 版本身份、安装路径、更新源与签名；适配现有构建；生成 Windows 候选安装包 | 从旧自定义版更新后，配置和新格式历史保留，统计继续累计，无法安装官方缓存 |
| 5：自动同步 | 正式版检测、升级分支、验证、候选构建、正式发布及失败停止 | 一次真实或可追溯的历史升级演练；冲突和失败不会发布；成功包可从自定义渠道更新 |
| 6：资源与用量验收 | 真实负载与高基数压力；误差分析；日报对照；清理和跨日演练 | 交付实际资源、空间与偏差数据，说明未验证项；更新使用说明和用户可见 changelog |

阶段顺序可以结合，但不能先开放自动更新再补签名与保留验证。每阶段完成可回溯提交，不为凑数量拆提交；未得到当前会话发布授权前只准备候选结果，不自行启用远端计划任务或正式发布。

### 9.1 旧实现退役

新实现验证通过后，扫描旧统计目录、Tauri 命令注册、导航、预览入口、旧测试与旧语言键的引用。只删除本次旧统计专属且已无引用的内容；保留官方公共模块和用户资料。确认安装包中只有一个统计入口、一个采集任务和一套新存储路径，不让旧采集器后台继续运行。旧代码可通过 Git 历史追溯，不靠保留废弃执行路径回退。

## 10. 资源与精度验证设计

### 10.1 性能和空间

使用相同机器、内核配置与负载，对比关闭/开启统计的增量开销。记录硬件、提交、连接数、目标基数、时长、工具和原始结果。

| 负载 | 关注点 |
| --- | --- |
| 空闲、少量长连接 | 空闲唤醒、CPU、写盘频率、页面隐藏后无查询 |
| 约 100 / 500 活动连接 | 快照解析、内存基线、采集耗时、写入队列 |
| 约 1000 活动连接及高基数短连接 | 是否积压、内存是否有界、代理吞吐变化 |
| 24 小时采集、30 天合成历史 | db+wal+shm 总占用、清理后复用、查询时延、启动内存 |

初始工程目标（待阶段 1 测量修订，不是已达成承诺）：常规 100～500 连接下新增内存控制在约 32 MiB；统计后台平均 CPU 低于一个逻辑核的 1%；常用排行查询 p95 在约 200 ms 内。Windows CPU 指标需换算并注明计量方式。

30 天数据库初始预算按约 256 MiB 评估，必须同时注明身份基数与模拟方法；高基数不承诺同样体积。优先精简重复文字和索引、压缩时间粒度，不以删除长尾解决超预算。预算不自动等于运行时硬限制，正式保护阈值依据可用磁盘和基准定稿。

### 10.2 流量验证

- 对受控 HTTP 下载/上传记录应用实际传输字节、内核观测增量和统计结果；避开压缩/缓存，说明口径差异。
- 分别运行单一大文件、多并发长连接、大量短连接、TCP/UDP 和直连混合代理。报告绝对差值、相对差值以及无法识别的字段，不只选一个有利样本。
- 规则切换、嵌套组、同域名多 IP、同名不同路径进程都要能在详情中核对；不因为汇总重复计数。
- 采集暂停/恢复、请求超时、重启、清空后保留活动连接、休眠恢复分别核对是否重复累计。
- 日报与同时间/route 的无搜索排行合计一致；搜索只影响排行及对应详情，不影响标明“全部地址”的独立日报。
- 验证 UTC+05:30 日界及夏令时短日/长日，降采样前后日报和地址分布均不跨日、重复或丢失。
- 持续高流量连接中插入一次请求超时，验证可信连接恢复后保留累计量；另测真实重启、消失连接和计数倒退，不能为减少漏计而重复计数。代理与直连不混算，未知和缺口单独说明。
- 至少进行一次实际日常使用观察；如果每天误差目标未能验证或短连接误差明显超出期望，如实记录，先评估采样策略，不自行升级为内核改造项目。

### 10.3 存储和升级验证

验证事务重试、分钟降采样重跑、写失败、容量暂停、损坏/未知格式、清空与待写竞态、正常退出和异常终止；异常终止允许尚未落盘数据丢失，但不能重复计入已经提交的批次或破坏已有库。

验证旧新包安装身份、版本比较、签名错误、缺失安装包、官方缓存、配置/数据库迁移失败和回退；备份失败不得继续安装，核对恢复旧配置及配套组件后的代理和统计行为。

推送一个自定义标签只应触发一套自定义发行；同步官方参考标签不得发布安装包。分别验证手动 updater、默认分支 push 及合并上游工作流后的隔离仍有效。旧版目标、改指标签和维护线基准并发变化必须停止自动发布。自动发布证据覆盖实际产物，编译不能替代安装演练。

定向自动测试只用于上述确实可能造成错误统计或升级丢数据的行为；新写最小的行为验证，旧测试仅供发现问题，不复制旧实现假设；随旧实现删除失去意义的用例。不添加大批模板测试或与实现逐句对应的用例。

## 11. 完成交付标准

最终交付应包含：可安装的 Windows 自定义版本、可追溯源码、实际上游基准、自定义更新配置、统计数据位置和保留规则、升级/回退方法，以及性能/空间/误差的实测结论。

用户应能直接回答：今天哪些地址用了最多代理流量，它们属于哪个进程，命中了什么规则；今天大概用了多少，哪些时段没有记录。无须理解内部采样机制才能完成主要操作。

只有自动同步、构建、发布和客户端升级均实际演练过，才能宣称自动更新完成。未配置的密钥、未验证的平台或尚未演练的上游版本必须明确列出。
